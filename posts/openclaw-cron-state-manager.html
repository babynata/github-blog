辅助 Openclaw 定时任务稳定运行的 Skill

2026.05.264 minOpenclawSkill定时任务Agent状态管理
Skill 仓库：https://github.com/babynata/cron-state-manager

我在使用 Openclaw 上的高频场景一般是一些定时任务：每日推送、状态追踪、定时提醒。在长时间高度使用后，我发现了一些稳定性方面的问题：

  1. 任务没执行，发现后多次需要通过重启 gateway 才能解决
  2. 任务执行报错，且排查和解决机制较弱，需要多轮引导才能解决
  3. 任务上下文混乱，一些需要记录状态的任务会搞错记录顺序甚至丢失记录

为了解决以上问题，我设计了一些机制去保证任务能长时间稳定运行。

1. 每次执行开新 Agent，互不干扰

定时任务每次调度时，会单独 spawn 一个临时 Agent 来处理本次任务。这个临时 Agent 拥有独立上下文，跑完就销毁，不会影响主会话，也不会影响其他定时任务。

就算某个任务挂了，也是它自己挂，不会拖垮全局。

2. 状态读写分清楚，谁写谁读不打架

有状态任务容易乱，根源在于多个 Agent 同时读写同一个状态文件。我的方案是：Worker 只读不写，主会话只写不读。Worker 生成内容时读取状态文件，用户回复后由主会话来更新状态。

两边各干各的，就不会出现记录顺序错乱甚至丢失的情况。

同时，Worker 不碰 memory 目录，人类记忆和任务状态彻底分开，上下文不会互相污染。

3. 写文件时先写草稿再替换，绝不写坏

状态文件如果被多个进程同时读写，很容易损坏变成半截 JSON。我的做法是先写到临时文件，确认写完整了，再加锁替换原文件。

读的时候也有锁保护，冲突了就自动重试几次。就算读写撞上了，文件也不会坏；真读不出来就返回空值，任务照样能跑下去，不会直接崩溃。

4. 执行过程全记录，出了问题翻日志就能定位

以前任务报错排查很费劲，要反复引导用户看这里看那里。现在每个任务执行时，stdout、stderr、耗时、退出状态都会自动记录到日志文件里。

所有任务的运行状态汇总在一个看板文件中，连续失败 3 次以上会自动告警。消息发送后也单独记录 delivery 状态，发了还是没发一目了然。

出了问题直接翻日志，不再需要多轮引导排查。

5. 状态不猜不填，用户没说的就是没发生

一个很容易被忽视的问题是：系统会自动帮用户“填默认值”，比如默认用户喝了 500ml 水，或者根据时间推算应该喝了多少。这样会导致状态失真，后续数据全错。

我的原则是：用户没有主动回复确认的数据，绝不自动填充。用户说喝了多少就记多少，用户没说话就保持空白。

保证状态记录准确可信，后续基于此生成的内容才不会跑偏。

6. 先看进程在不在，再决定要不要重启

以前任务没执行，第一反应就是重启 gateway，其实很多时候 gateway 进程还在，只是某个配置警告导致退出码非零。

我现在用进程探活来判断 gateway 到底挂没挂，而不是只看退出码。这样可以避免盲目重启，减少不必要的操作。

写在最后

以上就是我为 Openclaw 定时任务设计的稳定运行机制。核心思路很简单：隔离执行、读写分离、原子保护、完整监控、不猜数据、精准重启。

如果你也在用 Openclaw 跑定时任务，并且遇到过类似的稳定性困扰，欢迎试试这个方案。
